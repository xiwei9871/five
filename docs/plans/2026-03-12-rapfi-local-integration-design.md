# Rapfi 本地二进制接入设计文档

**项目类型：** 五子棋浏览器游戏外部引擎接入  
**创建日期：** 2026-03-12  
**目标范围：** 为现有前端项目新增一个本地 Node 服务，包装 `Rapfi` 二进制作为更强的 `hard` 模式 AI。

---

## 1. 目标与边界

### 1.1 目标

- 现有 `hard` 模式不再依赖浏览器内的简化搜索，而是优先走本地 `Rapfi` 引擎。
- 前端交互尽量保持不变，用户仍通过当前页面选择 `hard` 难度和落子。
- 当本地引擎服务不可用时，前端能够自动回退到当前本地 `hard` AI，避免功能中断。

### 1.2 本轮边界

- 仅支持“本机运行服务 + 前端本地调用”的模式。
- 仅为 `hard` 难度接入 `Rapfi`；`easy` 和 `medium` 保持现状。
- 不做云部署、不做账号系统、不做在线多人。

### 1.3 外部依赖

- `Rapfi` 官方仓库与 release
  https://github.com/dhbloo/rapfi
- `Rapfi` 默认通过 `Piskvork` 文本协议与外部程序通信。
- `Rapfi` 运行时需要其配置和网络权重文件位于可执行文件附近，官方 README 明确说明了这一点。

---

## 2. 当前项目现状

- 当前仓库只有 Vite + Vue + Pinia 前端，没有后端服务层。
- AI 决策全部在 [src/stores/game.ts](/Users/booboo/Desktop/claude%20code%20test/five/src/stores/game.ts) 中同步完成。
- `hard` 选择最终落点依赖 [src/utils/ai.ts](/Users/booboo/Desktop/claude%20code%20test/five/src/utils/ai.ts)。

因此，接入 `Rapfi` 的最小可行路径不是重写前端，而是新增一个本地服务，把“给定局面 -> 返回 AI 落点”变成 HTTP 接口。

---

## 3. 方案比较

### 3.1 方案 A：本地 Node 服务包装 Rapfi 二进制（推荐）

- 前端通过 `fetch` 调本地服务。
- Node 服务通过 `child_process` 启动 `Rapfi`，通过标准输入输出发送 `Piskvork` 协议命令。
- 服务把前端棋局转换为引擎局面，再返回一个 `{ x, y }` 落点。

优点：

- 与当前架构兼容度最高。
- 强度提升最直接。
- 易于调试和回退。

缺点：

- 需要本地额外启动一个服务。
- 需要下载并管理外部二进制与权重文件。

### 3.2 方案 B：浏览器内运行 Rapfi WASM

优点：

- 不需要本地后端服务。

缺点：

- 接入复杂度高。
- 构建和兼容性风险更大。
- 当前项目没有这条构建链基础。

### 3.3 方案 C：纯前端继续强化现有 AI

优点：

- 无外部依赖。

缺点：

- 难以在短期内达到 `Rapfi` 级别强度。

### 3.4 结论

选择方案 A。

## 4. 核心架构设计

### 4.1 组件划分

新增：

- `server/rapfi-service.ts`
  负责启动和管理 `Rapfi` 子进程。
- `server/http-server.ts`
  暴露本地 HTTP API，例如 `POST /api/ai/rapfi-move`。
- `src/utils/remote-ai.ts`
  前端请求本地服务的薄封装。

调整：

- [src/stores/game.ts](/Users/booboo/Desktop/claude%20code%20test/five/src/stores/game.ts)
  把 `playMove` 改成异步，在 `hard` + PvE 时优先调用远程引擎。
- [src/App.vue](/Users/booboo/Desktop/claude%20code%20test/five/src/App.vue)
  让落子事件支持异步执行，并在引擎思考时禁用落子。

### 4.2 协议与局面转换

前端提交的数据：

- 当前棋盘二维数组
- 当前玩家
- 棋盘尺寸
- 可选：超时预算

服务端负责：

- 将局面转换为 `Piskvork` 命令序列
- 启动一局分析
- 解析 `Rapfi` 返回的坐标

### 4.3 服务生命周期

- 服务启动时检查 `Rapfi` 可执行文件和必要权重是否存在。
- 若不存在，返回清晰错误，前端显示“外部引擎不可用，已回退本地 AI”。
- 引擎进程优先做成单例复用，避免每手都冷启动。
- 若进程异常退出，服务自动重启一次；仍失败则本次请求返回错误。

### 4.4 回退策略

若以下任一情况发生：

- 本地服务未启动
- `Rapfi` 二进制不存在
- 引擎超时
- 协议解析失败

则 `hard` 自动回退到当前本地 `chooseHardMove()`。

这保证页面仍然可玩，只是强度下降。

## 5. 用户体验设计

### 5.1 启动方式

新增两类命令：

- 启动前端：`npm run dev`
- 启动 Rapfi 服务：`npm run ai:server`

可再补一个并行命令：

- `npm run dev:full`

### 5.2 前端提示

- 当 `hard` 正在请求引擎时，棋盘应短暂禁用，防止重复点击。
- 若回退到本地 AI，可在状态区域显示简短提示。
- 不增加复杂控制台面板，本轮只保留必要状态提示。

---

## 6. 下载与文件组织

建议新增：

- `vendor/rapfi/`
  存放下载的 `Rapfi` 二进制、配置和权重文件

注意：

- `Rapfi` 使用 GPLv3。若将其二进制一起分发，需保留许可证和源码指向。
- 本轮先满足本地开发运行，不做对外打包分发流程。

## 7. 测试策略

### 7.1 单元测试

- 前端 API 客户端请求和错误回退逻辑。
- Store 在 `hard` 模式下优先调用远程引擎，失败后回退本地 AI。

### 7.2 服务测试

- 服务在缺少二进制时返回明确错误。
- 服务能把一个简单局面转换为引擎请求并解析出坐标。

### 7.3 集成验证

- 启动本地服务后，在页面选择 `hard` 模式能完成一手响应。
- 关闭服务后，页面仍可继续落子并回退到本地 `hard` AI。

---

## 8. 风险与控制

- 风险：下载到的 release 资产不包含当前平台可执行文件  
  控制：优先使用官方 release；若缺失，再改为源码编译。

- 风险：`Piskvork` 协议处理细节出错  
  控制：先做最小命令链路，只支持本项目需要的标准 15x15 自由规则局面。

- 风险：前端异步化后引入重复下子或状态竞态  
  控制：在请求期间锁盘，并给 store 增加“AI 正在思考”状态。

---

## 9. 预期结果

完成后：

- `hard` 模式优先由 `Rapfi` 决策，棋力显著高于当前前端 AI。
- 现有前端界面仍可直接使用。
- 用户只需额外启动一个本地服务即可获得更强 AI。
